2. PRODUCT AND PLATFORM SCOPE

Status: IMPLEMENTED — Polish personal collection and lending tracker.
Product name: Moja Biblioteka / My Library. The interface is Polish, with a
fixed pl locale and Material localization delegates. Provider metadata may
contain foreign-language text or fallback labels.
Supported release target: Android. Flutter, Material 3, SQLite, local-first.
Accounts are not required. Backend, Firebase accounts/database/FCM and cloud
synchronization are not implemented; these capabilities are DEFERRED.
iOS release is DEFERRED even though platform files and some plugin setup exist.
This is a personal library product, not a social-network application.

Independent Android devices can exchange selected borrowing information through
QR codes and manually sent SMS messages. Each keeps its own SQLite database.
They do not automatically synchronize dates, returns, deletions or ownership.
The owner's local loan is authoritative for the lending relationship; a borrower
copy can remain outdated indefinitely until the user imports a newer code.

Evidence: lib/main.dart (MyLibraryApp, LibraryShell), lib/data/,
lib/screens/offline_loans.dart, lib/screens/loan_messaging.dart.

3. PERSONAL COLLECTION

3.1 Manual addition and metadata editing
Status: IMPLEMENTED.
Purpose/workflow: use Add Book, enter title and author, optional ISBN/barcode,
condition and cover, then explicitly save. Book Details -> Edytuj książkę opens
the prefilled shared form. Required title/author are nonblank in the UI; editing
also enforces them in the repository. Conditions: Nowa, Dobry, Zużyta.
Data: add creates books plus one added history event atomically. Edit changes
title, author, barcode, condition and optionally cover for the same ID; preserves
createdAt, description, directory, loan fields and previous history. Real changes
update updatedAt; unchanged edits are no-ops and metadata edits add no loan event.
Constraints: valid ISBNs normalize; blank codes become NULL. ISBN-10 and its
equivalent 978 ISBN-13 share a duplicate-comparison identity. Existing legacy
duplicates are preserved, not merged. The exact-text unique index is a backstop;
repository rechecks under the transaction lock. DuplicateIsbnException produces
"Książka z tym numerem ISBN już istnieje." and permits correcting/retrying.
Limitation: manual storage intentionally also accepts non-ISBN barcodes. ISBN
checksum validation for scanning/lookup is not an ISBN-only save restriction.
Offline: all manual add/edit operations and managed local covers work offline.
Evidence: lib/main.dart (AddBookScreen, BookDetailsScreen.edit),
lib/data/library_repository.dart (addBook, updateBook, _assertUniqueBarcode),
lib/models/isbn.dart; test/add_book_screen_test.dart,
test/edit_book_screen_test.dart, test/library_repository_test.dart,
test/sqlite_repository_audit_test.dart. Merged PRs #1, #3, #12.

3.2 ISBN scanning and manual ISBN lookup
Status: IMPLEMENTED; physical scanner/camera checks: RELEASE VALIDATION PENDING.
Purpose/workflow: Add Book -> scanner, scan and validate, query Open Library,
review result and confirm prefilling; alternatively type ISBN and explicitly
choose Pobierz dane z ISBN. Lookup itself never saves a book.
Screens/actions: camera preview, torch, loading, result confirmation and Polish
no-match/network/timeout/retry feedback. Scanner formats are EAN-13, EAN-8 and
QR; content must normalize to a checksum-valid ISBN-10 or ISBN-13. Not every

Manual lookup fills empty title/author/cover fields and preserves user input;
responses for a changed ISBN are ignored. Save remains explicit.
Data: draft metadata only until save; no loan/history writes from lookup.
Network: Open Library metadata needs internet; failure leaves manual entry
available. No complete offline metadata catalog is included.
Evidence: lib/screens/scan_book_screen.dart, lib/main.dart (lookupIsbn),

5. OWNER LENDING, DATES, HISTORY AND REMINDERS

5.1 Lending, return and permanent giveaway
Status: IMPLEMENTED.
Purpose/workflow: available book -> Wypożycz książkę -> borrower name -> explicitly
select date or Bez terminu zwrotu -> review book/person/date -> confirm. Only then
does lending commit; QR opens afterward. Canceling QR/SMS never cancels a saved loan.
The same sheet offers Oddaj na stałe with separate giveaway confirmation.
Return uses Oznacz jako zwróconą and clears borrower/loan/due fields.
Data: book status available/borrowed/given and loan fields, one appropriate
borrowed/returned/given history event per successful transition, active loan mapping,
reminder opt-in reset. New lending starts reminders off.
Constraints: nonblank borrower/recipient; repository reads current row and rejects
invalid or stale transitions without overwriting metadata. UI starts giveaway from
an available book; repository also supports a matching borrowed-to-given transition.
That broader repository capability is not a separate borrowed-book giveaway UI.
Offline: fully local. No scan-to-return/lend shortcut or remote return notification.
Evidence: lib/main.dart (LendSheet, BookDetailsScreen.lend/returnBook),
lib/data/library_repository.dart (_transitionLoan);
test/library_repository_test.dart, test/sqlite_repository_audit_test.dart,

5.2 Global and per-book history
Status: IMPLEMENTED.
Purpose/workflow: Historia lists newest events with book-title snapshot, detail
and date; Historia książki in details shows newest 50 events for that ID, ordered
timestamp DESC then id DESC, with loading/empty/retry handling.
Data: history actions added, borrowed, returned, given, return_date_changed,
loan_extended. Opening details/QR creates no extra history. Deleting a book removes
its history; edits preserve historical titles and earlier events.
Constraints: exactly one appropriate event for each successful state/date change;
no-op/failed operations create none. Metadata editing is not a lending event.
Mixed legacy timestamp offsets/device clocks limit guaranteed global chronology.
Offline: fully local.
Evidence: lib/screens/book_history_section.dart, lib/main.dart (HistoryScreen),

5.3 Return-date change and extension
Status: IMPLEMENTED.
Purpose/workflow: borrowed details -> Zmień termin zwrotu or confirmed clear;
Przedłuż wypożyczenie -> +7/+14/+30 days or custom -> preview -> confirmation.
Data: return_date and updated_at plus exactly one history event in one transaction.
Ordinary changes/clearing use return_date_changed. Extensions use loan_extended,
never an extra borrowed or return_date_changed event. Borrower, original lending
date, status, metadata and prior history remain unchanged.
Constraints: changed ordinary dates are today/future; unchanged overdue dates
are no-ops. Extensions must be later than both prior term and today. Presets add
calendar days to the saved term, not today. No saved term requires custom date;
an overdue preset still in the past cannot be confirmed. Repeated targets cannot
create another successful event. Existing export revisions advance on date change.
Offline: local. Reminders reconcile after commit, retaining opt-in even when
clearing the date temporarily makes a reminder ineligible.
Evidence: lib/screens/return_date_section.dart, lib/screens/loan_extension_dialog.dart,
lib/models/return_date.dart, lib/data/library_repository.dart (_updateReturnDate);
test/change_return_date_test.dart, test/change_return_date_widget_test.dart,
test/loan_extension_test.dart, test/loan_extension_widget_test.dart. PRs #9, #10.

6. OFFLINE QR LOAN SHARING — TASK 19

Status: IMPLEMENTED; two-physical-device workflow: RELEASE VALIDATION PENDING.
Purpose/workflow: confirm owner lending first, display invitation QR, or reopen
Pokaż kod QR for the active loan without lending again. Recipient opens Pożyczone
od innych, scans QR or pastes standalone code, reviews unverified metadata and
explicitly confirms import. Share/copy fallback and local deletion are available.
Data: owner_loan_instances, loan_transfers, borrowed_loans; no transfer of ownership,
no owned-book insertion and no authority to lend/give a borrowed record.
Protocol: moja-biblioteka: + bounded Base64URL UTF-8 JSON; version 1,
loan_invitation. Carries stable transfer/loan/book IDs, bounded title/author,
optional ISBN/owner, original borrowing date, optional due date, issuance/revision.
Current owner generator omits owner display name. Codes exclude borrower names,
covers, descriptions, private paths, notification IDs and full history.
Constraints: exact duplicate import is a no-op. Higher revisions must preserve
transfer/book/original borrowing/owner identity and nondecreasing issuance.
Stale, same-revision conflicting or transfer-collision imports fail transactionally.
New lending periods receive new instance IDs; unchanged QR reopening preserves
bytes. Legacy active loans receive a persisted ID once. Local status is preserved
on revision import; its column is not a complete borrower return-management UI.
Offline: QR and manual-code operations need no network. Devices remain independent.
Limits: untrusted claims, no cryptographic identity/ownership proof; no automatic
sync, verified installation URL or deferred deep-link installation guarantee.
Retain the code and import manually after obtaining a trusted installer.
Evidence: lib/models/loan_transfer.dart, lib/screens/offline_loans.dart,
lib/data/library_repository.dart (loanInvitation, importLoan, deleteBorrowedLoan),
test/offline_loans_test.dart, test/offline_sharing_test.dart;
docs/offline-loan-protocol.md. Merged PR #14.

7. SMS INVITATIONS AND EXTENSION REQUESTS — TASK 20

Status: IMPLEMENTED; native composer/carrier/two-device QA:
RELEASE VALIDATION PENDING.
Purpose: exchange explicit invitations, requests and decisions between independent
local stores, without accounts/backend or automatic synchronization.

Workflow/screens:
1. Owner confirms loan, then Wyślij informacje SMS prepares readable Polish text
   plus the same v1 invitation code used for QR.
2. Owner opens native SMS composer, reviews recipient/body and presses Send.
   Recipient copies only the code into Pożyczone od innych and confirms import.
3. Borrower opens the imported loan, chooses Poproś o przedłużenie and a later
   future date. Preparing a request stores it locally without extending the loan.
4. Borrower explicitly sends through the SMS app. Composer launch does not mark
   sent/pending. A separate confirmed Zapisz, że wysłano prośbę declaration records
   local waiting status, with delivery explicitly unverified.
5. Owner manually pastes request, previews book/borrower/current/requested date
   and request ID with identity warning, then explicitly approves or rejects.
6. Approval rechecks active instance/book/date/revision under the SQLite lock.
   It updates the authoritative owner loan, revision, one loan_extended event and
   decision atomically. Reminder opt-in survives; reconciliation follows commit.
   Rejection records a decision without extending.
7. Owner reviews and explicitly opens/sends decision SMS; saved decisions can be
   reopened/resend without another extension. Canceled composer cannot undo approval.
8. Borrower manually pastes approved confirmation, reviews old/new dates and
   authenticity warning, then explicitly applies to their matching local loan.
   Exact duplicate confirmation is a no-op; stale/conflicting/replayed messages
   cannot regress a newer term. No local recorded request is required when the
   confirmation's expected loan/date/revision match.

Data/validation: loan_messages role/request/loan/state/request/decision; loan_contacts
for optional explicitly saved recipient number. Prepared, pending, approved,
rejected and imported are local states, not delivery receipts. Bounded v1 types:
extension_request, extension_approved, extension_rejected. Invitation decoder stays
invitation-only. Rejected decisions can be sent/read, but borrower confirmation
import accepts extension_approved only; rejection import/status application is
not implemented. No automatic rejection-state update on borrower device.
Offline/network: prepare/import/store locally offline; SMS delivery may require
carrier service and incur charges, including multipart Polish messages.
Native Android ACTION_SENDTO + smsto: + sms_body only opens composer.
No automatic SMS sending, SMS inbox reading, restricted SMS permissions, contacts
access, Firebase/FCM, backend, delivery confirmation or cryptographic authentication.
Share/copy fallbacks exist when composer unavailable. User confirms every imported
update. Base64 is not encryption; SMS is not end-to-end encrypted.
Phone: optional, max 40 characters, restricted phone syntax; stored only by explicit
Zapisz numer tylko na tym urządzeniu, blank save removes. Never in QR/message body;
only passed as recipient. Role/loan isolation applies even on one device.
Deletion/privacy: explicit borrower-record deletion removes borrower-role messages
and contact atomically; explicit owned-book deletion removes all associated owner
messages, contacts and snapshots across historical/legacy instances. Normal
return/re-lending retains decisions/contact history for replay protection. Another
device's data and copies in SMS/clipboard/share destinations are unaffected.
Evidence: lib/screens/loan_messaging.dart, lib/services/loan_sms.dart,
lib/models/loan_message.dart, lib/data/library_repository.dart,
android/app/src/main/kotlin/com/kamilloo/mylibrary/MainActivity.kt;
test/loan_messaging_test.dart, test/loan_deletion_privacy_test.dart;
docs/offline_loan_messaging.md. Merged PR #15.

10. SQLITE AND DATA PRESERVATION

Status: IMPLEMENTED — my_library.db, schema version 5.
Source: lib/data/library_database.dart and lib/data/library_repository.dart.
Production location: join(await getDatabasesPath(), 'my_library.db').
Dates/timestamps stored as TEXT; application identifiers normally UUID strings.
Protocol version 1 is unrelated to SQLite schema version 5; loan transfer
revisions advance independently within that protocol.

Tables:
- books: id TEXT primary key; title, author, description (default empty),
  condition, directory, status, created_at, updated_at required; cover_url,
  barcode, borrowed_by, borrowed_date, return_date nullable.
  Partial unique idx_books_barcode applies to non-NULL barcode. Multiple NULLs
  allowed; ISBN semantic equivalence is repository logic, not this index.
- history: id primary key; required book_id, book_title, action, timestamp;
  nullable detail. book_id FK to books(id) ON DELETE CASCADE.
  idx_history_book_timestamp indexes book_id, timestamp DESC, id DESC.
- return_reminders: AUTOINCREMENT integer id; unique required book_id; enabled
  integer default 0. Intentionally no FK: disabled deletion tombstones support
  retrying native cancellation without keeping title/borrower.
- owner_loan_instances: book_id primary key and cascading FK to books;
  loan_id required unique. One active instance per owned book.
- loan_transfers: loan_id primary key; required encoded payload snapshot.
- borrowed_loans: loan_id primary key; transfer_id required unique; payload,
  revision required; local_status required default active. No ownership FK:
  independent borrower copies never become owned books.
- loan_messages: composite primary key (role, request_id); required loan_id,
  request, state; nullable decision. No ownership FK; repository handles cleanup.
- loan_contacts: composite primary key (role, loan_id); required phone.
  No ownership FK; explicit deletion uses role-aware repository cleanup.

Foreign keys enabled on configuration. No SQL CHECK validation for all domain
statuses/date formats; supported APIs enforce invariants. Do not infer guarantees
for arbitrary external SQL writes or corrupt/unsupported future schemas.
Related loan/history/reminder-reset/instance writes are transactional. Approval
also commits revision and decision atomically. Filesystem and OS notifications
cannot join SQLite's transaction; copying/cleanup/reconciliation have separate
failure boundaries. No destructive reset, reseeding or delete-and-recreate fallback.

Forward migration:
- v1 -> add history index (v2), reminders (v3), transfer tables (v4), messages/
  contacts (v5).
- v2 -> add v3/v4/v5 structures.
- v3 -> add v4/v5 structures.
- v4 -> add v5 message/contact tables.
- v5 -> reopen without upgrade DDL.
Sqflite upgrade callback is transactional. Existing books, timestamps, categories,
descriptions, history, cover references, reminder opt-in/IDs and transfer/borrower
rows must survive. Installed upgrade requires compatible app/signing identity.
Snapshots keep stable transfer/loan IDs and monotonic revisions; date changes of
exported loans advance revision inside the transaction, even when later reverted.
Requests/confirmations validate expected loan, date and revision to resist stale
or repeated updates. These checks do not authenticate a sender.

Explicit deletion follows sections 3/7; normal return is not privacy erasure.
Notification tombstones may remain; best-effort cover cleanup can leave orphans.
Legacy formatted/duplicate barcodes and absolute covers are preserved rather than
silently rewritten. Missing legacy images use placeholders. Corruption, storage
exhaustion, root access and future-schema downgrade are not automatically repaired.
Evidence/tests: test/history_migration_test.dart (v1/v2/v3 to v5 and reopen),
test/fixtures/legacy_library_schema.dart, test/loan_messaging_test.dart (v4 to v5),
test/sqlite_repository_audit_test.dart, test/loan_deletion_privacy_test.dart;
